# BoneSAGEPooled capscope read-through (junior ML engineer, round 3)

Numbers below are copied from the GUI dump. "Sweep" means the TRUNCATION SWEEP (LOSS) section; the tool says it takes one module's weight(s), replaces them with the rank-k SVD approximation (top k singular directions kept, rest zeroed), re-runs the frozen model on 4 batches, and reads the loss; "used rank" is the smallest k whose loss stays within +1% of the untouched loss 0.1749, and "marginal pressure" is the loss rise at k = used − 1. The panel also says the base loss varies by ±13.2% (std) between the 4 sweep batches, and the guide says that with a 1% tolerance the used rank is therefore "± a few directions", not an exact count. I kept that in mind everywhere below.

Global facts I checked before any per-module decision (the guide's "reading them together" list):
- No undertrained warning in the header. Every 128×128 or 128×256 weight has alpha between 2.39 and 2.99 (the guide's "2–6 well conditioned" band; alpha = Hill power-law fit to the top tenth of the eigenvalues of WᵀW). The only alphas outside that band (8.78, 6.46, 7.62 for the convs.0 leaves/container; 4.01, 2.02, 5.05 for the heads) are labelled "not reliable" because those matrices have only 15 (or 3–4) eigenvalues and the fit reduces to a single ratio.
- Dataflow edges are present (21 edges), so the carry / upstream logic could run.
- No module has dead units; the largest duplicate share is 23% (gcn.convs.0.lin_l), below the 35% the guide says matters. Highest "best unrelated CKA" is 0.952 (convs.0.lin_l vs convs.0.lin_r), below the 0.98 the guide uses for "two modules do one job".
- Dirichlet energy of the conv outputs in execution order: convs.0 0.374, convs.1 0.289 (77%), convs.2 0.431 (149%), convs.3 0.537 (125%), trunk 0.695. The guide says only the decay matters and oversmoothed needs < 0.05 and < 30% of upstream. Nothing is close to that; energy is not falling hop by hop.

## Decisions

1. **gcn.convs.0.lin_l and gcn.convs.0.lin_r (the two Linear(15 → 128) leaves of the first SAGE layer)**
   (a) Decision: do NOT widen the 128 outputs. Change the *input*: add / enrich the per-joint input features (currently 15).
   (b) Numbers: input dim 15, width 128; weight rank cap "input-capped (≤15)"; sweep used rank 15 / max rank 15 for both; marginal pressure +17% (lin_l) and +486% (lin_r); loss at k=6 is 2.10 (+1101%) and 4.48 (+2460%); loss at rank 1 is 3.11 and 6.82. Upstream carry 15. Activation rank @ 99% energy is 9 for both, numerical rank 15. Duplicate units 23% (lin_l), 6% (lin_r).
   (c) How produced: the weight is [128×15], so the guide says its rank can be at most min(in, out) = 15; the sweep truncates that weight to rank k and reads the loss; carry is "the narrowest width along the dataflow paths feeding this module", and a source module carries its own input width (15). Activation ranks come from the SVD of a 4096-row sample of the layer's output.
   (d) Reasoning: the loss needs every one of the 15 directions this weight can have (removing the 15th costs +17% / +486%, removing more explodes the loss). But 15 is the ceiling set by the 15 raw input features, not by the 128 output units. Making the layer 256 wide cannot give it a 16th direction, because the input only has 15. So the one place where the loss clearly *is* pressed (the first layer) is pressed against the input, and the fix is more informative input features. The 23% duplicate outputs on lin_l corroborate that 128 outputs from a 15-dim input are more than the information supports. The huge asymmetry (lin_r's last direction costs +486%, lin_l's only +17%) means one of the two SAGE paths (self features vs. neighbour mean) matters far more to the loss than the other; the guide explicitly says the tool cannot tell which child reads which tensor, so I would have to read the model code to name it.
   (e) Confidence: high on "don't widen, enrich the input"; medium on the path asymmetry interpretation.

2. **gcn.convs.0 (the SAGEConv container)**
   (a) Decision: leave the width alone; same conclusion as its leaves. Optionally its 128 outputs could be *narrowed* (see item 10), but that is a parameter-saving change, not an accuracy change.
   (b) Numbers: container sweep used 15 / 15, marginal pressure +647%, loss at rank 1 = 15.1; rank cap input-capped (≤15) "taken from the leaf that produces the container's output"; activation numerical rank 30, rank @ 99% = 17, effective rank 16.6; carry 15.
   (c) How produced: for a container the sweep truncates both children's weights to the same k at once; the activation numbers are the SVD of the container's own output (lin_l(agg) + lin_r(x)).
   (d) Reasoning: the whole layer needs all 15 directions it can have, jointly. The output tensor is 128 wide but its numerical rank is 30 (two rank-15 maps added), so the 128-wide output holds at most ~30 dimensions of information. Nothing about width will change this; only the input can.
   (e) Confidence: high.

3. **gcn.convs.1 (container) with leaves gcn.convs.1.lin_l and gcn.convs.1.lin_r**
   (a) Decision: leave alone. No widening.
   (b) Numbers: container used 61/128 (48%), marginal pressure +2%; sweep table: k=44 → +10.5%, k=25 → +54%, k=59 → +1.7%, k=63…128 all within tolerance (≤0.9%). Leaves: lin_l used 43 (+2%), lin_r used 82 (+1%), lin_r k=75 → +1.6%, k=44 → +11.9%. Alpha 2.82 / 2.65 (well-conditioned). 0–1% dead/dup. Rank cap square (≤128). Carry 15 for the leaves, 30 for the container.
   (c) How produced: as in item 1; the guide says for choosing the width of a layer use the *container's* number ("what this block needs when all of it is squeezed together"), and the leaf numbers only say which path inside carries the load.
   (d) Reasoning: when the whole layer is squeezed it keeps the loss within 1% at rank 61 and the loss is flat from about 60 up to 128 (every step there is ≤ 2%). So there are ~65 directions of width the loss does not care about; adding more will not help. The leaf sweep says lin_r (82) carries more load than lin_l (43), again the same path asymmetry as in convs.0, but with tiny marginal pressure on both (+1–2%, which the guide calls "just outside the band"). The verdict boundary is irrelevant to me: the numbers say the loss is indifferent to the last ~60 directions.
   (e) Confidence: high for "don't widen"; medium for "could be narrowed" (used rank is ± a few directions given the ±13.2% batch spread, and the guide says container and leaf sweeps can disagree because truncation is not monotone).

4. **gcn.convs.2 (container) with leaves gcn.convs.2.lin_l and gcn.convs.2.lin_r**
   (a) Decision: leave alone. This is the fullest conv layer but it is still not pressed.
   (b) Numbers: container used 80/128 (63%), marginal pressure +2%; k=75 → +1.5%, k=44 → +10.8%, k=25 → +25.3%, k=15 → +70%; k=81…128 within tolerance. Leaves: lin_l 70 (+1%), lin_r 75 (+1%); lin_l k=44 → +3.9%, lin_r k=44 → +6.0%. Alpha 2.51 / 2.66 / 2.58. 0–3% dead/dup. Square cap. Carry 30 (leaves) / 60 (container).
   (c) How produced: sweep as above; the "loss at half the used rank" field is the loss at the largest swept k ≤ used/2 (here k=25, +25%).
   (d) Reasoning: taking away the 80th direction costs +2%, and the curve between 75 and 128 is flat (≤1.5%). That is exactly the guide's description of "the loss is indifferent to the last directions". A layer whose last used direction costs 2% is not asking for a 129th. There is a real climb below ~44 (+11%) and ~25 (+25%), so the layer *is* doing work, it just has ~50 directions of slack. Widening would add slack.
   (e) Confidence: high for "don't widen". I note that 63% vs the 60% "tight" line is within the ± few directions of batch noise, but I am not using the label anyway.

5. **gcn.convs.3 (container) with leaves gcn.convs.3.lin_l and gcn.convs.3.lin_r**
   (a) Decision: leave alone; if anything, this is the conv layer with the most unused width and the first candidate to *narrow* (e.g. to 64) if the goal were fewer parameters. Do not widen.
   (b) Numbers: container used 56/128 (44%), marginal pressure +1%; k=44 → +2.3%, k=25 → +11%, k=15 → +24%; k=57…128 within tolerance. Leaves: lin_l 34 (+1%; k=15 → +4.7%, k=25 → +3.3%), lin_r 50 (+1%; k=25 → +6.2%). Alpha 2.78 / 2.61 / 2.70. 0% dead/dup. Dirichlet 0.537 = 125% of convs.2 (not decaying). CKA with trunk.0 0.907 (consumer, and the guide says 0.8–0.95 between consecutive layers is normal).
   (c) How produced: sweep and Dirichlet as described above; Dirichlet = mean over edges of ‖xᵢ − xⱼ‖² divided by mean over nodes of ‖xᵢ − x̄‖² on centred node outputs.
   (d) Reasoning: the loss stays within 2.3% down to k=44 and within 1% from 56 up; this layer has the flattest curve of the four. It is clearly not width-limited. Message passing has not collapsed node distinctions (energy rose relative to convs.2), so the "fewer hops" advice does not apply; equally, I have no number that says a 5th hop would help (the guide says depth is not measured).
   (e) Confidence: high for "don't widen"; low for the narrowing size.

6. **gcn as a whole (the 4-layer SAGE stack)**
   (a) Decision: keep width 128 and depth 4. The stack is not width-limited; its only hard limit is the 15-feature input.
   (b) Numbers: joint sweep used 84/128 (66%), marginal pressure +2%; k=75 → +2.1%, k=44 → +24%, k=25 → +90%, k=15 → +212%, k≤9 → loss > 4; k=88…128 within tolerance. Alpha (median over the 8 weights) 2.72. Carry 15 at the stack input (the report says the carry then doubles 15 → 30 → 60 → 120 through the stack because both children of each SAGE layer are counted as separate producers; the guide calls that an over-estimate and "a rough floor, not a number to act on"). Dirichlet 0.374 → 0.289 → 0.431 → 0.537 across the four conv outputs.
   (c) How produced: this sweep truncates all 8 conv weights to the same k at once.
   (d) Reasoning: squeezing the entire stack to rank 84 leaves the loss within 1%, and squeezing to 75 costs only 2%. So ~40 of 128 directions are unused even when the whole stack is narrowed together. The curve does get steep below ~44, so the stack is doing real work with roughly 45–85 directions, and 128 is comfortable. The stack cannot be told it is starved of anything except input information (item 1). Depth: the tool measures dimensionality, not hops, so I cannot say from it whether a 5th layer would help; the only relevant hint is that node distinctions are not decaying (Dirichlet not falling), so more hops would at least not be blocked by oversmoothing.
   (e) Confidence: high for "width is fine"; "I don't know" for depth.

7. **trunk (Sequential: trunk.0 Linear(256 → 128), trunk.1 GELU, trunk.2 Linear(128 → 128), trunk.3 GELU)**
   (a) Decision: leave alone. No widening; it could probably be narrowed toward ~96 without a loss change, but I would not touch it while the goal is accuracy.
   (b) Numbers: container used 88/128 (69%), marginal pressure +1%; k=75 → +1.5%, k=44 → +8.2%, k=25 → +37.5%, k=15 → +277%; k=101, 128 within tolerance. trunk.0 used 65/128 (+1%; k=44 → +5.5%, k=25 → +25%), output-capped at 128 (its weight is [128×256]). trunk.2 used 67/128 (+1%; k=44 → +3.0%). Alpha 2.99 / 2.39 (median 2.69). 0% dead/dup. CKA: trunk.0~trunk.1 0.938, trunk.1~trunk.2 0.946, trunk.2~trunk.3 0.928, gcn.convs.3~trunk.0 0.907. trunk.1 and trunk.3 (GELU) have no parameters; their "used rank" 91 and 76 is the 99%-energy activation fallback, which the guide says is inflated by nonlinearities, so I ignore them.
   (c) How produced: same sweep; CKA = ‖XᵀY‖² / (‖XᵀX‖‖YᵀY‖) on the same sampled rows; the guide says a 0.8–0.95 chain between consecutive layers is normal and not redundancy (only > 0.98 with an unrelated module counts).
   (d) Reasoning: the trunk keeps the loss within 1% at rank 88 and within 1.5% at rank 75 when both of its weights are squeezed jointly; each Linear on its own needs only 65–67 of 128. So there are ~40–60 unused directions and the last used one costs 1%. The trunk is doing real work (rank 1 costs 4.88 loss, rank 25 costs +37%), it just has plenty of room. trunk.0 takes a 256-wide input (embedding ‖ rig-wide mean) but only needs 65 output directions of its 128 — so the 256-wide input is not overwhelming 128 outputs either. The high CKA chain inside the trunk is what the guide says a normal trunk looks like; it is not evidence that a layer is redundant. Widening the trunk would add directions the loss does not use.
   (e) Confidence: high for "don't widen".

8. **The three heads (binary_head Linear(128 → 4), side_head Linear(128 → 3), region_head Linear(128 → 4))**
   (a) Decision: leave alone. Their width is the number of outputs, which is set by the task.
   (b) Numbers: binary_head used 4/4, −1 dim = +28%, k=2 → +759%, k=1 → 2.75 loss. side_head used 2/3: k=2 gives loss 0.17492 (−0.0%, identical to base), k=1 → +272%. region_head used 3/4: k=3 gives 0.1716 (−1.9%, slightly *below* base), k=2 → +534%. Effective rank 3.6 / 2.4 / 3.3. CKA binary_head ~ region_head 0.882; side_head's best CKA is only 0.601 (trunk.3).
   (c) How produced: same sweep on the [4×128] / [3×128] weights; the panel field explicitly says the pressure here is "output head: every logit is load-bearing, not a width signal".
   (d) Reasoning: binary_head needs all 4 of its directions, which just means all 4 binary outputs carry loss. side_head (3 classes) and region_head (4 classes) are fine with one direction fewer than their output count; from ordinary training knowledge, a softmax over C logits is unchanged by a common shift, so C − 1 independent directions is exactly what a C-way softmax needs, so this is expected and not a defect. The guide says the tool sums the loss over heads and cannot decompose it, so it cannot tell me whether the plateau is one head fighting another. The guide's own suggestion for that ("pairwise cosine similarity of each head's gradients with respect to the shared trunk") is outside the tool. The fact that the binary and region heads read a very similar representation (CKA 0.88) while side_head reads something quite different (0.60) is at least a hint that "side" is the odd task out, but that is a guess, not a measurement of conflict.
   (e) Confidence: high that head widths should not change; "I don't know" on head conflict.

9. **Modules that look undertrained**
   (a) Decision: none. No training-length / learning-rate change is justified by the tool.
   (b) Numbers: all reliable alphas are 2.39–2.99; header has no undertrained warning; "loss at rank 1" is far above base on every swept module (1.22 to 15.1 vs 0.1749), which the guide says is the opposite of an undertrained checkpoint (where destroying a weight would cost nothing).
   (c) How produced: alpha from the Hill fit on WᵀW eigenvalues; rank-1 loss from the sweep.
   (d) Reasoning: the only alpha values above 6 are on 15-eigenvalue matrices, where the panel itself says the number is not a fit and the undertrained rule is not applied. I cannot use them.
   (e) Confidence: high (within what the tool can see; it says nothing about the training loss curve, which the guide tells me to check first, outside the tool).

10. **Modules that look redundant / removable**
    (a) Decision: nothing meets the tool's redundancy bar, so I would not remove any module. Two parameter-saving narrowings are *plausible* but not accuracy fixes: gcn.convs.0's 128 outputs (information rank ≤ 30) and gcn.convs.3 (used 56/128). I would not do either while chasing 0.977 → higher.
    (b) Numbers: convs.0.lin_l 23% duplicate units (threshold 35%); best unrelated CKA anywhere 0.952 (threshold 0.98); convs.0 output numerical rank 30 / rank @ 99% = 17; convs.3 sweep k=44 → +2.3%.
    (c) How produced: duplicates = output units whose |correlation| with an earlier unit exceeds 0.95 over the samples; CKA as above.
    (d) Reasoning: 23% duplicates and CKA 0.95 between the two convs.0 leaves both fall short of what the guide treats as "width already wasted"; the guide says below ~10% dead/dup "neither says much" and 23% is in between. Every module's rank-1 loss is large, so no module can simply be deleted. I flag the narrowings only as "could save parameters", with low confidence because the used rank is ± a few directions and a narrower layer would be retrained anyway.
    (e) Confidence: medium that nothing is redundant; low on the narrowing sizes.

## Overall recommendation

I would not add width anywhere. The only module where losing a direction really hurts is the first SAGE layer (removing 1 of its 15 directions costs +17% to +647% loss), and that layer's rank is capped at 15 by the 15 raw input features, so the first change I would make is to the input: add richer per-joint features (whatever the rig can supply beyond the current 15) and retrain the same architecture; I expect that to move the plateau if anything architectural can, because every later layer has 40–70 unused directions and their last used direction costs only 1–2%. If that does not help, the tool's guide points me next at the training data, the optimiser, and head conflict, which it does not measure; I would check the training loss against validation and measure the per-head gradient cosine on the trunk, not touch layer widths. Depth (a 5th SAGE hop) is not something this tool can argue for or against; oversmoothing is absent, so it is not ruled out, but I have no positive evidence for it.

## Unclear parts of the GUI

1. **Truncation sweep, container vs. leaf used rank (gcn.convs.1: container 61, lin_r child 82).** The guide says joint truncation can land within tolerance at a lower k than a single child, because the curve is not monotone. I still do not understand how the whole layer can survive at rank 61 when one of its two weights alone needs 82 with everything else intact. Question: when I set a layer's width, does the tool really intend me to trust 61 over 82, and what would go wrong if I trusted the leaf?
2. **Truncation sweep on gcn.convs.1.lin_r / lin_l vs. the rank of their input.** gcn.convs.0's output has numerical rank 30 (the sum of two rank-15 maps), yet convs.1.lin_r "needs" 82 directions of its weight. From the SVD paragraph I can see that truncating W keeps W's own top singular directions, which need not line up with the 30-dim input subspace, but the GUI never says this. Question: does a used rank of 82 here mean "82 dimensions of information", or just "W's spectrum is not aligned with its input", and does it matter for the width decision?
3. **Noise field, "±13.2% (std over 4 batches)".** The guide says used rank is then "± a few directions", but never says how many. Several tight/spare borders (63%, 66%, 69% vs 60%) are within a few directions. Question: is there a way to get an actual interval on used rank, or to run the sweep on more batches?
4. **Upstream carry (15 → 30 → 60 → 120).** The guide admits this doubling is an over-estimate when both children read the same tensor and says to treat it as "a rough floor, not a number to act on". If it is not to be acted on, why is it in the CAPACITY VERDICT INPUTS block for every module? Question: what would a carry of 120 at trunk.0 actually rule in or out?
5. **Weight spectrum (alpha) on 15-eigenvalue matrices.** The gauge still draws α = 8.78 in the "> 6 undertrained" zone while the text says "not reliable". Question: should I read anything at all into 8.78 vs 6.46, or should the number be hidden?
6. **Passthrough modules' "used rank" (trunk.1 GELU: 91/128, trunk.3: 76/128).** These are activation-energy fallbacks, but they appear in the same "used" column of the module list as sweep numbers, so trunk.1 looks like the fullest module in the network. Question: is the higher rank after GELU (91 vs 65 for trunk.0 before it) just the "inflated by nonlinearities" effect, or does it mean the GELU is creating usable directions?
7. **Dirichlet energy for lin_l vs. lin_r leaves.** The lin_l leaves are consistently much smoother than the lin_r leaves (0.197 vs 0.518; 0.285 vs 0.901; 0.310 vs 0.801). The guide says "a neighbour-mean path is smooth by construction", which tempts me to conclude lin_l is the neighbour path, but the same guide says the tool cannot tell which child reads which tensor. Question: is that inference legitimate, and why are leaf energies compared to the previous *container* (e.g. "53% of gcn.convs.0") when the guide says to read decay only between containers?
8. **Activation rank vs. sweep rank.** For most 128-wide modules the activation rank @ 99% energy is 27–45 while the sweep says 56–88. The guide says trust the sweep because small-variance directions may be what the heads read. Question: is there a chart that shows *which* low-variance directions the loss depends on, or is that unobservable here?
9. **Base loss 0.1749.** The header does not say whether the sweep batches are training or validation data, or what the summed loss is made of (three heads with what weights?). Question: is 0.1749 comparable to the training loss the guide tells me to check "outside this tool"?
10. **CKA heatmap.** gcn (the whole stack) has CKA 0.907 with trunk.0, 0.900 with trunk.2, 0.896 with trunk.1, and trunk.0–trunk.3 are all ≥ 0.92 with each other. The guide says a 0.9 chain is normal and the sweep's rank-1 loss (4.0 for trunk.0) says the layers matter. I accept that, but I could not tell from the heatmap alone whether the two trunk Linears are doing two different things or one thing twice. Question: is there a way to see what the trunk changed, rather than how much it preserved?
11. **"loss at half the used rank" on the heads.** For side_head it reports "0.6507 at k=1 (+272%)", identical to the marginal pressure, and for region_head "1.508 at k=1 (+762%)" while the table's k=2 row is +534%. Just a formatting oddity of the "largest swept rank ≤ used/2" rule, but it made me double-check the tables.
12. **Reading line.** It says "look at the input features, the data, the optimisation or head conflict before adding width" but the tool only measures the first of those (input width via the rank cap). Question: does the tool offer any measurement for the other three, or is that list purely advice?

## Things I had to guess

1. That "used rank k" on a container can be translated into "the layer could be k units wide". The guide says "for choosing the width of a layer, use the container's number", which I took as licence, but a rank-k weight and a k-unit layer are not literally the same object and the tool never trains the narrower model.
2. That the 15 input features are the raw per-joint features and that the rig can supply richer ones (e.g. more geometry). The GUI only shows "input dim 15"; the recommendation to "add input features" is the tool's, and whether such features exist is a data question the tool cannot see.
3. That lin_l is the neighbour-mean path and lin_r the self path, based on the lin_l leaves being much smoother in Dirichlet energy and on the guide's remark that "a neighbour-mean path is smooth by construction". The guide says explicitly the tool does not know this; naming the path needs the model code.
4. That the ±13.2% batch spread does not move any used rank far enough to change my conclusions. The guide says "± a few directions"; my conclusions rely on the shape of the (k, loss) tables (flat from ~75 up on every 128-wide module), which I believe is more robust than the exact crossing, but that is my judgement.
5. That the summed loss the sweep uses weights the three heads the way the training loss did. If a head is down-weighted in loss_fn, a module that matters only to that head would look "spare" here.
6. That the sweep batches are representative of validation data. If they were training batches, "the loss is indifferent to the last directions" might not transfer to the validation plateau.
7. That the binary_head's 4 outputs are 4 independent binary labels (from the task description, not from the GUI), which is why "used 4/4" is expected rather than a sign of anything.
8. That the module-list "used" column's percentage (e.g. "15/128 +17% input-capped") is the marginal pressure; the column header says only "used", and I matched it to the panels by value.
